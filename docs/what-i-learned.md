# What I Learned

## 1. LangChain4j: direct `ChatModel` calls beat `AiServices` for testability

LangChain4j offers two integration styles: the declarative `AiServices` proxy (define an interface, get an LLM-backed implementation at runtime) and calling a `ChatModel` directly. I went in expecting to use `AiServices` — it's the flashier pattern — but ended up wrapping `AnthropicChatModel.chat(SystemMessage, UserMessage)` directly inside `AnthropicLlmProvider`, itself one of three implementations of a hand-written sealed `LlmProvider` interface. The payoff was testability: `NoopProvider` is a trivial, zero-network implementation used in every test, and Mockito can `@Spy` a concrete permitted type freely. An `AiServices` dynamic proxy would have made both harder — you'd be mocking generated bytecode instead of a plain class. Sometimes the less magical LangChain4j feature is the one that makes the rest of the codebase easier to test.

## 2. Sealed interfaces are a real Java 21 correctness tool, not syntax sugar

`ValidationResult` (`ValidationSuccess | CompilationFailure | ExecutionFailure`) and `HealingResult` (`HealingSuccess | HealingFailure`) are both sealed. Every `switch` over them is exhaustive with no `default` — the compiler rejects the build if a new case is added anywhere and a `switch` doesn't handle it. That's not a style preference; it caught real omissions during development, at compile time, in a codebase where "silently swallow the new case" would otherwise be an easy mistake to make in error-handling code that's rarely exercised by hand.

## 3. Two IAM roles is where least-privilege stops being theoretical

ECS Fargate needs two separate roles: a **task execution role** (ECR pull + CloudWatch Logs, for launching the container) and a **task role** (S3/DynamoDB/SSM, for the application's own AWS SDK calls at runtime). They look redundant until you separate their permissions for real. During the security-hardening pass, a live deployment surfaced a genuine gap: the execution role could resolve SSM `secrets` at container startup, but the task role — used by Spring Cloud AWS's own SDK calls at runtime — was missing `ssm:GetParametersByPath`. Two roles caught a permission gap that one shared role would have masked. That's the actual argument for least-privilege: not paranoia, but making each failure mode visible instead of hidden inside one broad grant.

## 4. JavaParser is powerful precisely because it gives up on types

`StaticJavaParser.parse(String)` builds a full AST from raw source text with zero classpath and no symbol resolution — which sounds like a limitation until you remember the input is a GitHub Contents API response, not a compiled project. The `VoidVisitorAdapter` pattern for walking `MethodDeclaration` nodes was straightforward; what surprised me was how much you can determine about a codebase's conventions (JUnit version, mock library, base test class) from import statements and annotations alone, without ever resolving a single type. Trading type resolution for "works on any raw source string" was the right call for this problem.

## 5. A PR beats a comment, and the LLM is not the last line of defense

ADR-006 committed to delivering generated tests as a real branch + PR rather than a read-only comment — it's diffable, mergeable, and runs through CI like anything else. What reinforced that decision was watching `TestValidator` actually earn its keep: compiling and executing generated tests in-process caught both real engine bugs (a JUnit dependency missing from the runtime classpath) and, more often, cases where the LLM's own test made a false assumption about the code it was testing. A PR-based pipeline with a validation gate in front of it means a wrong test never reaches a human as something to trust — it just doesn't ship. Next: auto-triggering CI on `testgen/` PRs, auto-merge on green, and branch cleanup on merge.
